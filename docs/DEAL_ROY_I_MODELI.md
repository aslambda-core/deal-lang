## §1. .deal-компонент как служба дома — карта файлов ломтика

Урок дня 13.11 (фон): «панельная видимость живёт в ОТДЕЛЬНОЙ таблице tablitsa — RECIPES
мало; рецепт без pre не жилец». Прецедент саморегистрации: `lib/qwen_oblako_panel.py`,
`pulse/fon_razlozhit_sluzhba.py`. DEAL-ломтик повторяет живую механику:

| Файл ломтика DEAL | Что несёт | Прецедент |
|---|---|---|
| `<имя>.deal` | канон-AST компонента (единственный источник) | — |
| `<имя>_sluzhba.py` | рецепт `recept_имя()` + предполёт `_pre_имя()` (суд дубля пульсом, живость ctypes-судья `tools/avtostart_paneli._pid_zhiv`) | `pulse/fon_razlozhit_sluzhba.py` |
| регистрация в `launcher/services.py` | RECIPES["имя"] = recept_имя() | фон (коммит d0b6d3c2b) |
| строка в `launcher/tablitsa.py` | видимость панели: живость по пульсу/порту | строка fon_razlozhit |
| галочка в `launcher/avtostart_sluzhb.py` | подъём при входе | PO_UMOLCHANIYU["fon_razlozhit"]=True |
| `data/<имя>_puls.json`, `data/<имя>_status.json` | живость числом (правило 18: ребёнок назван, живость числом) | `data/fon_razlozhit_*` |

Разница с питон-ломтиком одна: тело службы — не питон-файл, а .deal-компонент, исполняемый
ВМ DEAL; карта файлов остаётся прежней, потому что панель и запуск судят службы по договорам
данных (порт/пульс/рецепт), а не по языку.

## §2. Кладка DEAL vs живая кладка — side-by-side

Живая кладка конвейера (пример `mcp_qwen_coder/queue/done/t_*.json`, суд hoden в
`most_nasos.py`: spec 20–2000 знаков с solve, tests ≥2 литеральных assert):

```json
{"id": "t_1795458_9ab4db", "source": "rd", "priority": "05",
 "spec": "solve(data: bytes) -> {\"размер\": len(data), ...}",
 "tests": "assert solve(b\"proba\")[\"размер\"] == 5\n...",
 "meta": {"rd_id": "RD-…", "оракул": "RnD/oraculy/RD-….py", "поручил": "ии:голова-насос"},
 "code": "<питон-текст>", "result": {"ok": true, "proverok": 3}}
```

Кладка DEAL — те же сёла, язык другой:

```json
{"id": "d_1795964_01f2ab", "source": "rd", "priority": "05",
 "цель": {"хеш_договора": "c4d5e6…", "имя": "цена_за_единицу"},
 "задание": [{"превращение": "ввести-сделку", "ast": {...}},
             {"превращение": "добавить-кейс", "кейс": {...}},
             {"превращение": "заменить-тело", "тело": [...]}],
 "свидетели_свои": [{"вход": {...}, "выход": ...}],
 "meta": {"rd_id": "RD-…", "слайс": 2431, "поручил": "ии:руки-8b"},
 "итог": {"стадии_пройдены": 8, "отказы": [{"стадия": 3, "виновник": "…", "исправлено": true}]}}
```

Разница по существу:

| Питон-кладка | DEAL-кладка |
|---|---|
| ИИ пишет текст solve + asserts | ИИ подаёт превращения над AST |
| суд hoden — регэкспы по тексту | стадии 1–3 компилятора — структурный суд |
| tests = литеральные asserts | свидетель = кейсы + скрытые верификатора |
| код может быть правдоподобным | непроверяемое не принимается стадией 4 |
| дедуп и потолок попыток — как есть | то же: заявка O_EXCL, износ, отступ |

## §3. Роли моделей — кто что подаёт в DEAL-конвейер

Роли назначаются функциями, не портами (прецедент `lib/roli_modelei.py`), бюджеты
ризонинга — `data/most_reazoning.json` (голова 12288, руки/фон до 500к — слово владельца 09.11):

| Модель | Порт | Роль в DEAL-конвейере | Почему ей |
|---|---|---|---|
| Голова LFM2.5-24B | 8080 | планы превращений (какие сделки, какой шов, какие свидетели), рецензия договоров | планирование и карты дома |
| Малые LFM 8B/24B | 8081 и др. | **кладки DEAL first-class**: подача превращений по слайсу | слайс 2–3к токенов влезает в малое окно; кладки уже малые (урок насоса: 24B-A1B закрывала формульные задачи) |
| Фон GLM-5.3-Flash | 8085 | рефакторинг длинных договоров (контекст 524288), переработка корпуса | «на 500 тысячах резать» — слово владельца 06.11 |
| Судья d1-omni-600M | 8084 | вероятностные суды кладки (choice/score: «превращение по смыслу цели?»), ОДИН проход без генерации | прецедент `lib/systemone.py` — дешевле парсинга текста |
| Облачные каналы (qwen/glm/gemini) | CDP | коллеги-архитекторы: разбор договоров до кладки, советы к карточке (прецедент ЦПР «сначала облако») | тяжёлое суждение, не решение |
| Песочница docker/process | — | исполнение свидетелей и карантинного яруса | отказ в безопасную сторону, `sandbox.py` |

Смежные вердикты наружу компилятора: компилятор детерминирован (часть 3 §6), модели
судят только то, что язык судить не может — смысл цели, полноту свидетелей как набора.

## §4. Перевозка .deal между узлами

Рой: server-03 (ядро) и lambda (реплика), связь — только полка на debug.lteam.ru
(прецедент `tools/roy_ochered.py` FtpPolka; прямой сети нет — решение владельца 24.09).
Правила перевозки DEAL:

1. **Компонент едет ФАЙЛАМИ, никогда перепечаткой** — живой урок 06–07.11: «в вместо in»,
   перепечатанное по памяти ломало латиницу/кириллицу. .deal-файл + манифест с sha256
   (прецедент Рой-жидкости: «7 складов едут ПО СКЛАДУ с манифестом sha256»).
2. **Реестр компонент-хешей на ядре**: пишет только ядро с номером аренды
   (прецедент `lib/roy_arenda_yadra.py` — ограда mozhno_pisat); реплики тянут манифест
   и качают «только отсутствующее» (рой-жидкость, `tools/pamyat_vygruzka/vlivanie`).
3. **Конфликт двух писцов** невозможен по конструкции: запись без действующего номера
   аренды отклоняется словами; худшая гонка двух писцов оставляет файл живым
   (прецедент гонки .chast 13.11 — `roy_yadro.zapisat` с обязательным писцом).
4. **Сверка при подъёме**: узел считает хеш полученного .deal и сверяет с манифестом;
   расхождение = отказ словами, файл перезакачивается.

## §5. Живой сценарий end-to-end (10 шагов, все файлы названы)

Задача: закрыть карточку RD-… «цена за единицу» DEAL-конвейером.

```
1. Владелец одобряет карточку (стандартная дверь tools/rd.py --одобрить)
2. Насос DEAL (аналог most_nasos.py) берёт карточку: у неё оракул в изоляции
   → подаёт договор цели кладке (превращения-план от головы, pachka-триаж)
3. Заявка O_EXCL: data/most_zanyatiya/RD-….json (прецедент насоса)
4. Кладка летит в очередь малой руки: mcp_qwen_coder/queue_vtoraya/pending/…json
   — формат §2 (цель+задание-превращения+свои свидетели), слайс 2.5к токенов
5. LFM 8B подаёт превращения по слайсу (лог части 2 §7-пример-5)
6. Компилятор: стадии 1–8; 2 отказа словами → исправлены ИИ → 8/8 стадий
7. Компонент в реестре DEAL (хеш, летопись, проекция)
8. Доводчик (прецедент mcp_qwen_coder/dovodchik.py): решение в RnD/reshenija/<rd>/,
   ход в карточку «компонент DEAL собран, свидетели зелёные (песочница конвейера)»
9. Карточка — на приёмке: владелец читает ПРОЕКЦИЮ компонента (читаемый вид —
   для него и существует) и вердикт оракула
10. Компонент-служба регистрируется ломтиком (§1) и поднимается дверью control.start
```

Никакой новой инфраструктуры: очередь, заявки, доводчик, приёмка, панель — всё уже
живёт; меняется payload кладки (§2) и появляется компилятор.

## §6. Переходный период — правила совместного проживания

| Правило | Почему |
|---|---|
| Храповик 600 строк остаётся для питон-части (костыли обучения) | решение владельца: предел не преодолен, стабильность не доказана |
| Для DEAL-файлов лимит — не строки, а узлы AST одной сделки (ПРОЕКТ-МЕРКА: ≤512 узлов, степень 1 растяжки: расколоть-по-шву — превращение №11) | «длинный файл для правки» в DEAL бессмысленно: правка адресуется договором; лимит стережёт читаемость проекции |
| Прибор ширины и направления ввозов (обсуждение 14.11) — не вводится сейчас | DEAL решает корень: канон и хеш-ввозы делают спор бессмысленным; приборы питон-дома — отдельные карточки |
| Питон-конвейер и DEAL-конвейер работают параллельно на живом доме | урок дома: дом не останавливается; миграция по компонентам за договорами |
| Каждый перенос компонента в тело дома — через приёмку владельца | правило Р28 не меняется языком |
